# GitButler on GPUI

An experimental native GitButler client built on [GPUI](https://gpui.rs), the UI framework behind Zed. It calls `but-api` in-process, so there is no Node runtime, IPC or JSON between the UI and GitButler.

## Run it

From the repository root, on macOS, Windows or Linux:

```bash
cargo build -p gitbutler-git --bins   # once per checkout: the askpass helper that push and fetch run
cargo run -p but-gpui
```

Each worktree builds into a `target` folder of its own, so a new one needs the helper too. `make run-but-gpui-without-xcode` builds it with the client.

On Linux, GPUI also links to libxcb, libxkbcommon and fontconfig: on Debian or Ubuntu, `sudo apt install libxcb1-dev libxkbcommon-x11-dev libfontconfig-dev`.

Started with `cargo run` on macOS or Linux, the status bar ends with a Build and restart button, right of Commands, which the palette also has. It builds the client again with the same profile, and `--features gpui_platform/runtime_shaders`, and the askpass helper beside it, showing cargo's output as it comes, in colour and with its progress bar, then restarts on the new binary in place, so `cargo run` and its terminal keep it. When the repository has more than one worktree with the client, it first asks which to build from. A failed build leaves the app running, with the output on screen. Hide keeps it building, the button then says Building…, and Cancel build stops it, with the compilers it started. Installed builds, and the desktop app's, don't show it.

The project list comes from the app data of the build's channel, which is `dev` by default. Build with `CHANNEL=nightly` (or `release`) to see the projects of an installed GitButler.

## What you can do

Keys are written as on macOS. On Windows and Linux, ⌘ is Ctrl and ⌥ is Alt, as the app's own labels show.

Any key can be changed in `keymap.json` in the settings folder, which Help › Open Keymap File (or the palette's Open keymap file, or Open in Settings › Keyboard) creates and opens in the editor picked in Settings › General, or in the system's app for JSON when none is picked. It's written as Zed's keymap is, and holds only what you change: its keys go over the app's own, `null` switches one off, and `unbind` takes a default key away from an action. The palette's Open default keymap opens the same way and shows every key the app binds and the action each runs. The app reads the file again each time it's saved and says Keys updated; what in it doesn't load goes on a card, and the rest still binds, or, when the file isn't JSON the app can read, the keys stay as they were.

Vim's keys work beside the arrows: j and k, h and l, gg and G, { and } between projects and branches, ]c and [c between hunks, n and N between matches in the diff, y to copy and : for the palette. t goes to a branch, as in the TUI, F2 renames, ? and ⌘/ list every key in Settings › Keyboard, ⇧⌘O clones a repository and ⇧⌘T opens the selected checkout in the terminal. On Windows and Linux, Delete discards or deletes what's selected and Ctrl+Shift+Backspace uncommits, as Ctrl+Alt+Backspace can end the desktop session there.

The app is built for watching what coding agents change. Reading their changes comes first, and committing by hand is there when you need it. It follows their changes as they land while any of its window shows. Hidden, behind another app's windows, minimized, on another Space or with the display asleep, it reads no changes and catches up once it shows again, so an agent at work costs a laptop's battery almost nothing while the app sits out of sight. It still asks the forge about pull requests and CI, every five minutes instead of every minute, as agents read what it last heard through `but`.

- **Uncommitted changes.** Every changed file as a diff, but for the repository's own linked worktrees inside the checkout, as Claude Code makes under `.claude/worktrees`, which are checkouts of their own. j and k step through files, ↑ ↓ through hunks, space and shift-space page through the diff, and ⌥⌘Z throws a hunk away (or the lines picked in it), with an Undo button in case you didn't mean it; with no commits yet, HEAD detached or no target set, GitButler's history can't take a discard back, so it asks first. The navigator's Main worktree row counts the lines they add and remove, in green and red, or how many files there are when none can be counted, as with binary files or more than 300 of them. ⌘↩ or "Commit…" opens the composer, where you check files or single hunks and pick a branch: the one ⌘↩ was pressed on, or one of whose commits it was, else the one you made last if you just made one, else the one you last committed to. It opens with every file checked, or with just those the file filter shows while it filters, and a file that turns up while it's open, as an agent writes one, starts unchecked. Opened over lines picked in the diff, or files ⌘-clicked in the list, it checks just those. Never the default branch (main): with no other, the commit goes on a new branch with a made-up name, as `but commit` does (⌘Z takes back the commit, then the branch), and dropping changes on the default branch does nothing. With nothing changed, the composer still opens and makes an empty commit; opened on changes that something else, as an agent, commits meanwhile, it says so rather than make an empty one. When the branch it shows is renamed or leaves the workspace meanwhile, as an agent can do, Commit and Amend say where the changes would go instead, and go there if you try again. The branch button, or ⇧⌘B while writing the message, opens a picker. Type to filter the branches and press Enter, or pick New branch to make one for the commit, named as typed, or with a made-up name when nothing is typed. With Run Git hooks on in the project's settings, committing in the main checkout runs the repository's pre-commit hook, then commit-msg, which can rewrite the message, and either one failing stops the commit and shows what it printed. The post-commit hook runs after the commit, which stays even if the hook fails; an error then shows its output. Changes a commit can't take, as hunks that build on another branch, are left out, and a card says which and why, naming the first few for each reason and counting the rest. Click a changed line's numbers to take just that line out, or, in a hunk that's out, to bring just that line in. The message you're writing stays with its project or linked worktree while the app runs, as what's checked does. The sparkle in the message box writes the message with AI from the checked changes, streaming it in, without a reasoning model's thinking or a code fence around it; anything already in the box guides it, and pressed again while it writes, it keeps what's written so far. A file a merge left with conflict markers, as an update can, shows as conflicted and first, counted on Uncommitted changes in the navigator, and starts unchecked in the composer and stays out of a drag or ⌘X of the changes, as a commit refuses it while it's conflicted. A Git repository cloned into the folder, not added as a submodule, says so and starts unchecked too, as committing it would record a submodule with nowhere to clone it from. Its conflicts show in place of the markers and resolve as a conflicted commit's do, between your changes and what the update brought (named after the target), or the sides the markers name after another merge: Apply in the banner above the files (⌘↩) writes what each keeps into the file, and marks it resolved once it has none left, in one step you can undo. In a JSON file or a notebook, what would leave it unparsable, as both sides kept with no comma between them, is refused while it parses with one side. Its menu can still mark it resolved as it is on disk, and discarding it takes it back to its last commit. When Git itself stopped partway through a rebase, merge, cherry-pick or revert, as an agent's can, a banner says so, and hovering it says how to finish it; the project's page does too. Committing or amending there, or making a branch in the main checkout, waits until it's finished, as during a `git bisect`.

  A changed image (PNG, JPEG, GIF, WebP, BMP or TIFF) shows before and after, side by side. So does an SVG, drawn sharp at its own size, an icon grown to 64 points so the change shows; the code button in its header shows its lines instead, and back. A diff with more than 24 SVGs, as snapshot tests leave, shows them all as text, as drawing them would take seconds. A submodule says which commit it points at, and which it pointed at before. Discarding one asks first, as it resets the submodule's checkout, or deletes a repository added but not recorded, and undo can't bring back what's in it.

  Diffs are drawn like but.dev's. A file's header has its type's icon, its name with the folder dimmed, its line counts and five squares split green and red as they are, and the file the cursor is in has a tab on its left edge. Each line has one number, the old one for a removed line and the new one otherwise, and a changed line has a bar down its edge, solid for an addition and hatched for a removal. The cards sit on the pane's white ground, as but.dev's do, and side by side a line with nothing across from it faces a hatched gap. Code and the lines' greens and reds take GitHub's colours, and UI text and code are Inter and Geist Mono at design-core's regular weight, 460.

  Above each hunk a grey box counts the unchanged lines left out before it (`36 unmodified lines`). Clicking it, or the button beside the file's line counts, shows those lines too, so the whole file reads top to bottom; the button hides them again.

  Diffs mark the words that changed within a line, and the box above each hunk names the function or type it sits in (`impl Counter › pub fn bump(&mut self, by: i32) -> i32`). When the rest of that scope is short, 50 unchanged lines or fewer across its hunks, they show it whole, as deltoids does; a longer one keeps three lines of context, with the hunk's box naming it. The box leaves out a scope whose first line shows just above the hunk's changes, and one the hunk before is in when no lines between them are left out. A hunk whose lines run on from the one above with nothing left to name has no box, and while the cursor is on it the cursor's tab runs down its lines instead; right-click them for its menu. Settings › Appearance › Whole scopes up to sets that limit to 20, 50 or 200 lines, and turning Semantic context off leaves out the names and the extra lines and skips reading the code for them. The extra lines are context only: picking, dragging and discarding act on the hunk as before. All of this comes from [deltoids](https://github.com/juanibiapina/deltoids), which parses the two sides with tree-sitter, in the 20 languages it knows (Rust, TypeScript, JavaScript, Python, Go and more, though not Svelte), for a file whose two sides come to 1 MB or less and that changes at most 4,000 lines.
- **A commit.** A header across the page, as but.dev draws it: the title, then who made it and when, its short ID (click to copy it), a quiet lock and "Signed" when it carries a GPG, SSH or X.509 signature (the tooltip names which; the app doesn't verify it), and whether it's pushed. An author shows as the same patterned circle in the same colour as on but.dev, drawn from their name. The button beside the title opens the rest of the message between those two lines, and double-clicking the title edits the message in place; past a dozen lines, the message and its edit box scroll, so the files stay in reach; what you type there waits for you while you look at other commits, and stays if saving it fails. Below sit its files and its diff. The ⋯ at the header's end opens the commit's right-click menu, which uncommits or discards it, adds an empty commit above or below (the selection stays where it was), starts a new branch ending at it, moves it into a new branch of its own, rewraps a message with lines too long for `git log`, and copies its ID, change ID or message. With a workspace commit selected, ⌘C or y copies its change ID, falling back to its full commit ID when it has no change ID; Copy commit ID in the menu always copies its full commit ID. ⇧⌘C or ⇧Y lists what else of it to copy, as the TUI's does: its short commit ID, message title, whole message or author (`name <email>`, Git's author, the agent when one wrote it), as well as both IDs. ⌘-click (ctrl-click off macOS) selects more commits along with it, and ⇧-click or ⇧↑ ⇧↓ selects a run of them from where the last other click left off, as in Finder, which the status bar counts. They stay in one stack, or one linked worktree's branches, so their changes make one diff: ⌘- or ⇧-clicking a commit in another selects just it, and ⇧↑ ⇧↓ stop at the stack's end. Dragging or cutting one of them takes them all, and a click without dragging selects just it; their right-click menu cuts or cherry-picks them, squashes them into the oldest, or into the one right-clicked, in its place, moves them to a new branch, or uncommits or discards them all (⌘⌫ too). Picked as one run of commits in one stack, across its branches too, the page shows their changes together, under a header counting them and naming their branches, as the breadcrumbs do; picked with gaps, it shows each one's own changes in turn, oldest first, each file's header naming its commit, as one range would bring in the commits between them too, and says so.
- **A conflicted commit.** Its conflicts sit in its diff, where they are in each file, with its conflicted files first and marked Conflicted. Each one shows the lines of what the commit now sits on (named after the target, and "main and below" further up a stack) and the commit's own lines, tinted as Lite and but.dev tint a merge conflict, with the words they differ in marked, and a button that shows how the lines were before either changed them. Above each, keep one side or both, edit what to keep in place (Return, or Edit), or have AI suggest a merge, which streams in as a suggestion to keep or change. A pick folds the conflict into what it keeps, with Change to pick again, and nothing changes until Apply in the commit's header (⌘↩) resolves every picked conflict in one step you can undo. A one-line banner above the files counts what's left, and says to start with an older conflicted commit in the stack when there is one; hovering it says why or what to do. Once a commit has none left, the stack's next conflicted commit comes up, the branches below it in another lane included. 1, 2 and 3 keep the first side, the commit's or both, A suggests, and each pick moves on to the next conflict. One GitButler marked conflicted while Git names no file to resolve, as a move between agents' branches holding the same files under other folders can leave, says so, and that Operations history can restore to before it. For conflicts with no lines to pick, like a file one side deleted, run `but resolve <commit>` in a terminal; such a file is listed with what the commit did to it, even when the commit's own diff leaves it out, as a deletion that conflicts keeps the file. A conflicted commit can't be uncommitted from its menu, the picks' menu or by dragging it to Uncommitted changes, as its files are one side's and the change it carries would be lost. Nor can it be squashed, into another commit or another into it, for the same reason. It checks the commit out, conflict markers and all, and the project then lists just "Editing a commit": its files, with their conflicts to pick between as above, Cancel to put the commit back as it was, and Finish to commit the files in its place (asking first while any are still conflicted). Until then the app turns down other operations on the project, apart from fetching. A branch with conflicted commits says how many on its page, and its Resolve goes to the oldest in its stack, which can be in a branch below or one its lane rests on; it isn't offered when that's in a linked worktree, whose conflicts resolve there.
- **A branch.** Its commits and combined diff, under a header across the page as a commit's has, so stepping between a branch and its commits moves nothing below: its name, how many commits it has, where they stand against its remote and any conflicted. A stack's page has one too. A branch starts folded, its commits behind a count, unless Settings › Appearance › Show branches' commits is on; one of its commits being selected shows them anyway. Clicking a branch selects it; the chevron before its glyph, a double-click, or ⇧→ and ⇧←, show and hide its commits, and ↑ and ↓ only select. With Open branches on click on in Settings, a click shows its commits too, and folds again those the last click showed, unless you opened or folded them yourself since, so the list doesn't grow by a branch with every click. A double-click whose first click showed them leaves them shown. A branch with no commits has a dot there instead, and says "empty" after its name, as but.dev's does. An empty one's page says it has no commits above what it starts on: the branch below it, or the one its worktree rests on, at the commit when that's below the tip, else the target. Hiding them over a selected commit selects the branch. A stack of two or more branches sits under a "Stack of N" caption, its branches a step in. Selecting the caption shows what its branches change together, as one diff; its chevron, a double-click, or ⇧← and ⇧→, fold them away, and folded, it names its top branch, to tell it from another stack as tall, counts their unpushed commits, shows a dot for unread ones and says when they last changed. ⇧← from a branch in it goes up to it. Its tooltip names the branches, top first. Right-click it to push the stack, land it on the target, start a new branch on top, or unapply it: each acts through its top branch, which takes the ones below along, as the branch's own menu does, so it doesn't push, land or unapply while that branch is unnamed, as when a linked worktree has it checked out. A linked worktree's stack only folds, pushes and takes a new branch on top. Its header says how it stands against its remote in plain words: on the remote, so many to push, so many to pull (and to push), or rewritten and needing a force push; one only behind its remote isn't offered a force push, as pulling is all it needs. Forcing the target branch itself, checked out and pushed, always asks first, as others' work builds on it, naming the newest of the commits only its remote has that it would drop. - **Linked worktrees.** A project with linked worktrees, like the ones agents work in, lists each worktree in a section of its own, separated by dashed lines. "Main worktree" comes first, over your stacks; each linked worktree follows, the one used last first, though not while the pointer is over the list, over the branches and commits made in it, from the branch it has checked out down to the target or the lane it rests on, its commits the target already has marked as landed. Under them, quieter, are the branches it rests on, nearest first: the first in each worktree says which one, and one it rests on below the tip says at which commit. Clicking one selects it where it's listed. Selecting a worktree's heading shows its uncommitted changes, which the heading counts. Its chevron, a double-click, or ⇧← and ⇧→, fold its branches; folded, the heading also counts their unpushed commits, and Main worktree's shows a dot for unread commits. Folding over the selection moves it up to the heading, and ⇧← from a closed branch goes there too. A green "active" on a heading means its files changed or its HEAD moved, as a commit moves it, in the last two minutes, as an agent at work does (the project counts as active then too). Its commits drag, cut and paste as yours do: reorder or squash them, move them between it and your stacks, or drop one on the worktree's heading to uncommit it there. Rewriting the branch the worktree has checked out takes the worktree along and updates its files, and is refused when that would overwrite its uncommitted changes. Its branches move only within its lane, and yours go under its branches from its heading (see below); a branch moved across would leave the worktree detached and bring along the commits it started from. Its commits and branches are edited from here as yours are too: reword, discard, uncommit, squash, add empty commits, select several with ⌘ and ⇧, rename a branch (the worktree follows the new name) or move a commit to a new branch. Its branches push from here, taking the ones below along, your stack's they started on included, as the snackbar counts. Its pull requests are made, merged and set to auto-merge from here too, a new one pushing first and going into the nearest branch below with an open one, else the target. Pulling, landing and unapplying reach past the worktree, so its branches don't offer them. Its edits don't undo either. New branches go on top of or below its branches, or end at one of its commits, as on yours; one on top of the branch it has checked out becomes its checkout, so its next commits go there, as its snackbar says. A branch stacked under the one it has checked out can be deleted, its commits joining that one, as in Lite; the one checked out stays with the worktree, and the delete can't be undone, as the oplog doesn't keep a worktree's branches. Files move in and out of them as anywhere else: drag or cut a worktree's uncommitted files into any commit, or onto any branch to commit them there with no message yet (double-click its title to write one), drop your files on a worktree's commit or branch, and move, split off or uncommit the files of its commits. Its commits' files uncommit into the worktree itself, as that's where their checkout is. Select a linked worktree to watch its changes as they're written, its heading counting their lines as Main worktree's does; e opens a file from the worktree in your editor. Its page is laid out as Main worktree's, and commits the same way: Commit… or ⌘↩ opens the commit box, whose checked files, hunks and lines go on the branch the worktree has checked out (there's no other to pick), and Amend adds them to that branch's newest commit. ⌘↩ from one of its branches or commits comes here, rather than to Main worktree. Its files and hunks discard as yours do, by the hunk's button, ⌥⌘Z, ⌘⌫ or a right-click, but always ask first, as a worktree's discard can't be undone. Right-clicking its heading reveals or copies its folder, archives it to hide it, or deletes it from disk after asking, uncommitted files and all; its branch stays. Worktrees that exist when GitButler first lists a project's worktrees start archived, and Show an archived worktree… in the project's menu brings one back. A worktree with nothing uncommitted and no commit or checkout in the last 12 hours is inactive, and the project lists its inactive worktrees under an Inactive worktrees heading, folded to how many there are, as Network worktrees folds the work on your other machines. The selection in one keeps them listed, and folding them over it, or ⇧← from a folded one, selects the heading. Selecting the heading shows an overview of what's left in them, so what's done can go: how many there are, their commits, those no remote has and how long the quietest has been quiet; how many hold commits only here, landed, have every commit pushed or have none; and a lane for each, of its commits a day over the last 30 days and how long it's been quiet, which a click opens.
- **Network worktrees.** Signed in to your mesh (Settings > General), a watched project's card lists its checkouts on your other machines after its own worktrees, under a Network worktrees heading, and draws them as it draws worktrees, with a computer for an icon. They show as last read from the moment the app opens, and the mesh's answer a few seconds later changes only what changed, so the card doesn't grow under you. Under each are its branches, counting unpushed commits, and under an open branch its commits. A chevron, a double-click, ⇧→ or ⇧← folds them as a worktree's, and branches start folded or open as Settings say local ones do. A checkout with nothing going on, no uncommitted files and no branch with commits that haven't landed, isn't listed. Selecting something of a project's elsewhere fetches its branches here with `but mesh fetch`, from the copy the mesh keeps (also while that machine is offline), one at a time and the selected one first, into refs of the mesh's own, checking nothing out; a branch whose newest commit is here already isn't fetched. The right-click menu opens a checkout or branch on but.dev, copies a checkout's path, or, with the workspace checked out, offers Apply here for a branch, which brings its commits over, outside the project's queue so a slow network holds up nothing else, and applies it to your workspace, named `<branch>-from-<machine>` when one here has its name. It works while that machine is offline too, from the copy the mesh keeps. The filter finds a checkout by its machine or worktree name, or by its branches' names. The app reads the mesh every minute while the window shows, and at once when a project starts being watched or the window shows again; a read that fails keeps the last one, so a network blip or a broken daemon leaves the card as it was. While signed in, each project watched here is added to the mesh daemon's list if it isn't on it, so your other machines see its work; the daemon watches its files and reports a change within seconds. It all goes through the `but mesh` command-line tool (`but-mesh` on the `PATH` or in `~/.local/bin`), so without it nothing shows.
- **Operations history.** The last row of each project lists what GitButler did to it, newest first under each day, including what agents ran from the CLI: each operation as what it was done to, after a glyph for what it did (a commit made, changes amended into one, commits squashed, something reworded or renamed, thrown away, done to a branch, brought in from the target, taken back, a snapshot), and its time, faint. The glyph is green for what the operation added, blue for what it rewrote, red for what it threw away and amber for what it took back, and hovering it names the operation, so every row leads with its commit or branch and a run of commits made reads as the commits. One with nothing to name, as a commit that failed to sign, shows the operation's name, faint. What an operation was done to comes from comparing its snapshot with the next one, or with the workspace now for the newest, with the workspace applied or one branch checked out on its own, matching commits by change ID so a rebase alone changes nothing, and telling an amend by the same parent with other changes: the commit it made, amended or reworded, the one a squash took away and the one it went into, how many it cherry-picked, the branch it created, renamed or unapplied, how many commits an update brought from the target; else what the log says. `but amend` logs an amend as a squash, so one that took no commit away is listed as the amend it was. An undo, redo or restore shows what the operation it took back was done to, its glyph's hover naming that operation; a restore picked here has a clock for its glyph, apart from ⌘Z's undo arrow. Work done outside GitButler between two operations counts as the later one's; a linked worktree's isn't in the snapshots, so what was done there shows only by the log's name for it. Select an operation to see, over the files it changed, a header as a commit's: what it was and when, the branch it was on, and each commit or branch it changed, an amended one marked so and a reworded one with its old title; a commit the workspace still has opens on a click. Restore the project to how it was before it from its right-click menu or the header's ⋯, which also copies its snapshot's ID; the restore can be undone too, and it refuses, as ⌘Z does, to go back past what moved a linked worktree. Above the list, a filter (/ goes to it) finds operations by what they did or to what, reading up to 600 operations of a long history to find one, the menu beside it picks which kinds show (commits made, commits rewritten, changes thrown away, branches, updates, undos and restores, snapshots, and other), and + takes a snapshot of the project as it is now, to come back to later, with a message to say what it's for if you give one. A snapshot reads as its message, or "Manual snapshot", beside a camera. Opening a project's history shows its newest operation, and a history that can't be read says why in place of the list.

Moving things works by drag and drop or by ⌘X on the source and ⌘V on the destination:

| Move | onto | does |
|---|---|---|
| a commit, or the selected ones | a branch | moves them to the top of that branch |
| a commit, or the selected ones | another commit | moves them there, between the two commits under the pointer; on a commit's middle, squashes them in |
| a commit, or the selected ones | uncommitted changes | uncommits them, a worktree commit's into that worktree |
| a commit | New branch, below the stacks and any linked worktrees while dragging | moves it into a new branch of its own (also in its menu) |
| uncommitted files | a commit | amends that commit |
| uncommitted files | a branch | picks that branch and those files for the next commit; a linked worktree's files, or onto a worktree's branch, commits them there with no message |
| a commit's file | another commit | moves the change between commits |
| a commit's file | uncommitted changes | uncommits just that file, a worktree commit's into that worktree |
| a branch | another branch | stacks it, with the branches above it, on top of that one; dropped on its lower half, or with ⇧, below that one instead. A linked worktree's branches only move within its lane |
| a branch | a linked worktree | puts it under the worktree's branches |
| a stacked branch | Unstack, below the stacks and any linked worktrees while dragging | moves it into a stack of its own (also Unstack in its menu). ## How it's built

- `src/backend` is the only code that touches GitButler crates, and `src/backend/annotate.rs` the only code that touches deltoids. It turns `but-api` results into plain structs (`model.rs`) and diffs into hunks of lines (`diff.rs`), and runs every call on a tokio pool with large stacks, since GitButler's graph walks and push futures overflow the small stacks of GPUI's worker threads in debug builds.
- `src/state` holds the projects, selection, what's been cut and which commits you've opened. `load.rs` loads and watches workspaces, `background.rs` fetches and asks the forge on its own, and `seen.rs` tracks what you've looked at; `mutation.rs` runs a project's mutations one at a time and queues the rest; `saved.rs` picks what the app remembers between launches, which `src/backend/saved.rs` keeps in `gpui-state/state.sqlite` in the app data directory, one per channel as the project list is. Deleting that folder resets the app.
- `src/navigator.rs` (its menus in `navigator/menu.rs`) and `src/detail/` (its file lists in `file_list.rs`) are the two halves of the window; `src/transfer.rs` decides what a drop or paste does, so both input methods agree. `build.rs` compiles in the file-type icons from `packages/ui-react`, and `src/ui/file_icons.rs` reads that package's map to pick one, so they match Lite and but.dev.
- `src/backend/mesh.rs` runs the `but-mesh` program for the mesh, reading its JSON, as the mesh has no library; `src/state/mesh.rs` polls it, `src/navigator/mesh.rs` draws each card's checkouts elsewhere, `src/detail/machine.rs` fetches and shows what's selected of them and `src/settings/mesh.rs` is its Settings row. AGENTS.md has the rules that keep it apart from the rest and harmless when the mesh misbehaves.
- `src/backend/metrics.rs` sends GitButler's metrics and error reports to PostHog, as the desktop app and the CLI do, under the same settings and ID: launches, the operations you start with the workspace's shape in counts, once an hour while you use it what you've opened and a few settings, errors shown, projects that stop reading, and panics and crashes. `metrics/crashes.rs` leaves a file while the app runs, so the next launch knows when the last one didn't quit, and on macOS reads the system's crash report for it then. Nothing sent names a branch, file or anything you wrote, and development builds only log it, at debug. Both are on unless turned off, as the CLI's are, with no question asked first: Settings › General › Metrics turns error reports and usage metrics off for all of GitButler's apps, as the desktop app's Telemetry page does, and off stops them at once. The welcome screen says so in one line at the bottom, with links to the privacy policy and to those switches, as VS Code's welcome page does. It runs off the UI thread and gives up quietly, so it can't slow or break the app.
- `src/edits.rs`, `src/pr.rs`, `src/detail/resolve.rs` and `src/projects.rs` hold the actions on commits and branches, pull requests, conflicts and projects; `src/settings/` is the Settings window.
- `src/keymap.rs` binds the keys in `assets/keymaps/default.json`. `src/palette.rs` is the command palette, `src/overlays.rs` the menus, prompts, modals and snackbars above the window, and `src/status_bar.rs` the strip along the bottom.
- `src/ui` has the small components GPUI doesn't ship: buttons, a text field, a scrollbar, diff rows, and the empty states with ui-react's drawings, read from `packages/ui-react` and coloured for the theme.

It is a member of the main workspace, so `cargo check --workspace` catches `but-api` changes that break it. GPUI is a git dependency on Zed that brings around 900 crates and needs Rust 1.98. It builds on macOS, Windows and Linux. On each, the headers are the window's title bar: drag one by a spot with no button to move the window, and double-click it to do what double-clicking a title bar does there, which on macOS is what System Settings › Desktop & Dock says (zoom, fill, minimize or nothing) and elsewhere maximizes the window or restores it. On Linux it opens on Wayland or X11, whichever the session runs, and draws its own window frame where the desktop leaves that to the app, as GNOME does on Wayland: a shadow whose band resizes the window, the buttons Windows has, and the window menu on a right click on a header. The desktop app's binary can start it too: built with `gitbutler-tauri`'s `builtin-gpui` feature, it runs this client instead of the web one when started with `--gpui`, or always when GitButler's `featureFlags.gpui` setting is on, which only this client's Settings › Experimental › Open this app at start shows (or an edit of `settings.json`), on the same settings, accounts and keychain entries. If it can't open its window, as when the GPU's drivers can't draw it, the web app opens instead. Started that way, it asks the web app's update feed for a newer version as often as the web app would, and a card at the bottom right offers it. Its Update installs it with the web app's updater, which the same binary runs without a window when started with `GITBUTLER_INSTALL_UPDATE`, the card says how much has downloaded, and once it's installed the app starts again on it (on Windows the installer closes the app and starts the new one). Its Release notes opens What's New, on a nightly too. Later hides the card for four hours, after which it comes back. Meanwhile New version beside Sign in stands in for it and brings it back on a click, showing the download's progress at one width so the filter beside it holds still. The card hides while a modal is open, What's New included. GitButler › Check for Updates… asks the feed at once and shows the card, or says the app is up to date. With the update interval at 0, as builds that don't update themselves set it, the client neither checks nor shows the menu item.

## Development

- `GITBUTLER_GPUI_APPEARANCE=dark` (or `light`) overrides the system appearance.
- `E2E_TEST_APP_DATA_DIR=<dir>` points GitButler's app data and settings at a sandbox.
- Build with `cargo build -p but-gpui --features dev-script` and set `GITBUTLER_GPUI_SCRIPT=<file>` to replay clicks, drags and keystrokes and save screenshots of the window. `src/dev.rs` documents the commands. The window never shows, the app stays out of the Dock and never takes the keys from the app in front, and the run quits when the script ends.
- `scripts/drive.sh run <file>` builds that and runs the script against app data of its own, killing it after a timeout. `scripts/drive.sh start`, then `step <command>…` and `stop`, drives one run a step at a time, saving a screenshot after each.
- In a build of your own (no `CHANNEL` of `nightly` or `release`), Settings has a Developer page. Its Show FPS puts the frames drawn in the last second in green in the window's top right corner. When the slowest frame of the last three seconds drew at under 80% of that pace, its own pace shows beside them in amber, as `60 · 30`, so a single hitch shows that the count over a second hides. A gap of over a second is the window not drawing, as while it's hidden, and starts it over. While it shows, the window draws every frame it can, so the number is how fast it can draw: the display's rate when nothing is slow, and at most about 30 while another app is in front, as GPUI slows an inactive window.
