# GitButler on GPUI

An experimental native GitButler client built on [GPUI](https://gpui.rs), the UI framework behind Zed. It calls `but-api` in-process, so there is no Node runtime, IPC or JSON between the UI and GitButler.

## Run it

From the repository root, on macOS:

```bash
cargo build -p gitbutler-git --bins   # once: the askpass helper that push and fetch run
cargo run -p but-gpui
```

The project list comes from the app data of the build's channel, which is `dev` by default. Build with `CHANNEL=nightly` (or `release`) to see the projects of an installed GitButler.

## What you can do

The app is built for watching what coding agents change. Reading their changes comes first, and committing by hand is there when you need it.

The left side lists every project. An expanded project starts with Main worktree, which selects your uncommitted changes and counts them, then its stacks, branches and commits; with linked worktrees it heads a section of its own, as the next part says. A collapsed project's row sums up what it holds: uncommitted files, its worktrees' included (amber), unpushed commits (blue), commits the target has that you don't (amber) and how many worktrees it has. An expanded project's row keeps only the commits behind the target, as its rows count the rest, and a branch counts its commits only while they're hidden. Hover a count to see what it counts. When a reload adds rows above the row under the pointer, like an agent's new commit, the list scrolls to keep that row where it is. A file watcher keeps expanded projects current; collapsed ones aren't loaded at startup or watched. The collapsed ones share a card under "More projects", the first eight then "N more", each with how long ago Git last recorded something done in it. A branch's commits fold the same way past eight; once unfolded, "Show fewer" at the end folds them again, staying under the pointer as "N more". Its heading folds the card away, filters it by name (Enter opens the first match), adds a project, and under ⋯ sorts it by name or last activity and shows all of it or just the projects active in the last 7 days; the choices stay for the next launch. A green "active" dot marks a project whose files or commits changed in the last two minutes, and a teal dot marks commits you haven't opened yet. Mark all as read in a branch's right-click menu clears its dots without opening each, and Mark as read does the same for picked commits. Commits the app itself rewrote don't count as new, and neither do a linked worktree's, whose changes were there to watch as they were written.

The right side shows whatever is selected, under a bar on the window's grey ground, as but.dev's location bar: the button that shows or hides the navigator (.), then a breadcrumb naming the project, the worktree as the navigator heads it (Main worktree, or a linked worktree's name), and the branch, whose crumbs link back to them. Drag the right edge of the navigator or of a file list to resize it (a grey line marks the edge under the pointer), and double-click the edge to reset it; the widths are remembered.

- **Uncommitted changes.** Every changed file as a diff. j and k step through files, ↑ ↓ through hunks, space and shift-space page through the diff, and ⌥⌘Z throws a hunk away, with an Undo button in case you didn't mean it. The navigator's Main worktree row counts the lines they add and remove, in green and red, or how many files there are when none can be counted, as with binary files or more than 300 of them. ⌘↩ or "Commit…" opens the composer, where you check files or single hunks and pick a branch: the one you made last if you just made one, else the one you last committed to. The branch button, or ⇧⌘B while writing the message, opens a picker. Type to filter the branches and press Enter, or pick New branch… to make one for the commit. With Run Git hooks on in the project's settings, committing runs the repository's pre-commit hook, then commit-msg, which can rewrite the message, and either one failing stops the commit and shows what it printed. The post-commit hook runs after the commit, which stays even if the hook fails; an error then shows its output. Click a changed line's numbers to take just that line out, or, in a hunk that's out, to bring just that line in. The sparkle in the message box writes the message with AI from the checked changes, streaming it in; anything already in the box guides it. A file a merge left with conflict markers, as an update can, shows as conflicted and first, counted on Uncommitted changes in the navigator, and starts unchecked in the composer, as a commit refuses it while it's conflicted. Its conflicts show in place of the markers and resolve as a conflicted commit's do, between your changes and what the update brought (named after the target), or the sides the markers name after another merge: Apply in the banner above the files (⌘↩) writes what each keeps into the file, and marks it resolved once it has none left, in one step you can undo. Its menu can still mark it resolved as it is on disk, and discarding it takes it back to its last commit. When Git itself stopped partway through a rebase, merge, cherry-pick or revert, as an agent's can, a banner says so and how to finish it, and the project's page does too.

  A changed image (PNG, JPEG, GIF, WebP, BMP or TIFF) shows before and after, side by side. So does an SVG, drawn sharp at its own size, an icon grown to 64 points so the change shows; the code button in its header shows its lines instead, and back. A submodule says which commit it points at, and which it pointed at before.

  Diffs are drawn like but.dev's. A file's header has its type's icon, its name with the folder dimmed, its line counts and five squares split green and red as they are, and the file the cursor is in has a tab on its left edge. Each line has one number, the old one for a removed line and the new one otherwise, and a changed line has a bar down its edge, solid for an addition and hatched for a removal. The cards sit on the pane's white ground, as but.dev's do, and side by side a line with nothing across from it faces a hatched gap. Code and the lines' greens and reds take GitHub's colours, and UI text and code are Inter and Geist Mono at design-core's regular weight, 460.

  Above each hunk a grey box counts the unchanged lines left out before it (`36 unmodified lines`). Clicking it, or the button beside the file's line counts, shows those lines too, so the whole file reads top to bottom; the button hides them again.

  Diffs mark the words that changed within a line, and the box above each hunk names the function or type it sits in (`impl Counter › pub fn bump(&mut self, by: i32) -> i32`). Both come from [deltoids](https://github.com/juanibiapina/deltoids), which parses the two sides with tree-sitter.
- **A commit.** A header across the page, as but.dev draws it: the title, then who made it and when, its short ID (click to copy it), a quiet lock and "Signed" when it carries a GPG, SSH or X.509 signature (the tooltip names which; the app doesn't verify it), and whether it's pushed. An author shows as the same patterned circle in the same colour as on but.dev, drawn from their name. The button beside the title opens the rest of the message between those two lines, and double-clicking the title edits the message in place. Below sit its files and its diff. The ⋯ at the header's end opens the commit's right-click menu, which uncommits or discards it, adds an empty commit above or below, starts a new branch ending at it, moves it into a new branch of its own, rewraps a message with lines too long for `git log`, and copies its ID, change ID or message. ⌘-click (ctrl-click off macOS) picks more commits along with it, and ⇧-click or ⇧↑ ⇧↓ picks a run of them from where the last other click left off, as in Finder, which the status bar counts; the picks' right-click menu squashes them into the oldest, or into the one right-clicked, in its place, or uncommits them all.
- **A conflicted commit.** Its conflicts sit in its diff, where they are in each file, with its conflicted files first and marked Conflicted. Each one shows the lines of what the commit now sits on (named after the target, or "Commit below" further up a stack) and the commit's own lines, tinted as Lite and but.dev tint a merge conflict, with the words they differ in marked, and a button that shows how the lines were before either changed them. Above each, keep one side or both, edit what to keep in place (Return, or Edit), or have AI suggest a merge, which streams in as a suggestion to keep or change. A pick folds the conflict into what it keeps, with Change to pick again, and nothing changes until Apply in the commit's header (⌘↩) resolves every picked conflict in one step you can undo. A banner above the files counts what's left, and says to start with an older conflicted commit in the stack when there is one, as this one is rebuilt on it. Once a commit has none left, the stack's next conflicted commit comes up. 1, 2 and 3 keep the first side, the commit's or both, A suggests, and each pick moves on to the next conflict. For conflicts with no lines to pick, like a file one side deleted, run `but resolve <commit>` in a terminal. It checks the commit out, conflict markers and all, and the project then lists just "Editing a commit": its files, with their conflicts to pick between as above, Cancel to put the commit back as it was, and Finish to commit the files in its place (asking first while any are still conflicted). Until then the app turns down other operations on the project, apart from fetching. A branch with conflicted commits says how many on its page, and its Resolve goes to the oldest in its stack, which can be in a branch below.
- **A branch.** Its commits and combined diff, and Push, under a header across the page as a commit's has, so stepping between a branch and its commits moves nothing below: its name, how many commits it has, where they stand against its remote and any conflicted. A stack's page has one too. Click the chevron before its glyph, double-click it, or press ← to hide its commits behind a count, and again, or →, to show them; a branch with no commits has a dot there instead, and says "empty" after its name, as but.dev's does. Hiding them over a selected commit selects the branch. A stack of two or more branches sits under a "Stack of N" caption, its branches a step in. Selecting the caption shows what its branches change together, as one diff; its chevron, a double-click, or ← and → fold them away, and folded, it counts their unpushed commits and says when they last changed. ← from a branch in it goes up to it. Its tooltip names the branches, top first. Right-click it to push the stack, land it on the target, start a new branch on top, or unapply it: each acts through its top branch, which takes the ones below along, as the branch's own menu does. A linked worktree's stack only folds. When its remote has commits it doesn't, as when a teammate or an agent elsewhere pushed, its page lists them and Pull brings them in with its own commits on top, and a force push asks before dropping them; when that would leave its commits conflicted it stops and says so, with Pull anyway to go ahead; its menu can also replace the branch with the remote's version instead. A branch with others stacked on it can't pull yet. Its right-click menu adds a branch on top or below, an empty commit on top, squashes all its commits into one, takes it out of its stack, or unapplies it. The bottom branch of a stack can land on the target, its commits going straight onto it and pushed, skipping review; from the top branch the whole stack lands. Both ask first, as a push can't be undone. With Land branches directly on in the project's settings, the branch's header offers Land in place of Create pull request, with or without a forge; Create pull request stays in its menu.
- **A branch's pull request.** A card on the branch's page: its title, number, state, labels, how its CI checks stand (a failed one by name, opening why it failed), and who's been asked to review it, with a button to open it.
- **A project.** Under a header with its name and an icon, which opens a picker of emoji to give it one, as but.dev's repository page does (search by name, Return takes the first, Remove icon clears it); the navigator shows the emoji before its name, and the app keeps it with its other preferences. Where it is, when it last fetched (and why a fetch failed, or that it has no remote to fetch from), a nudge to connect an account when it's on a forge none is connected for, and its target's history: the commits new on the target first, then the ones your workspace already has, each with the pull request that landed it, paging further back on request. Select one to see its diff. Fetch and Update (rebase every stack onto the target's new commits) are in the header. Update first works out whether rebasing would conflict any commits or uncommitted changes, and stops with Update anyway when it would. Afterwards it says which branches have conflicted commits, selecting the first, and which landed branches it removed. A new project starts with one branch checked out rather than the GitButler workspace, as in the desktop app, and its page says it's working on that branch directly. Switch to the workspace leaves it for the workspace, to work on several branches at once. Until then a new branch goes on top of the one checked out and is checked out in its place, and there's nothing to unapply.
- **Branches.** Next to History at the end of each project: the branches the workspace doesn't have applied, local ones first, then the ones only a remote has, like a teammate's, with a filter by name or author. Each shows what it changes against the target, as its pull request would, and Apply adds it to the workspace (a remote branch gets a local branch first). Local branches can be deleted. The selected branch lists its commits under it: select one to see it on its own, then drag it onto a branch or commit in the workspace, or press Cherry-pick (also in its right-click menu) and ⌘V there, to copy just that commit in.
- **Linked worktrees.** With Linked worktrees on in Settings (GitButler's experimental worktree support), a project with linked worktrees, like the ones agents work in, lists each worktree in a section of its own, separated by dashed lines. "Main worktree" comes first, over your stacks; each linked worktree follows, over the branches and commits made in it, from the branch it has checked out down to where it started. Commits the target already has are left out. Selecting a worktree's heading shows its uncommitted changes, which the heading counts. Its chevron, a double-click, or ← and → fold its branches; folded, the heading also counts their unpushed commits, and Main worktree's shows a dot for unread commits. Folding over the selection moves it up to the heading, and ← from a closed branch goes there too. A green dot on a heading means its files changed in the last two minutes, as an agent at work does (the project counts as active then too). Its agent works on its branches in place, so its commits and branches don't move from here, apart from putting one of your branches under them (see below), and anything else that would change them asks you to make the change in the worktree. You can look at them, copy their names and ids, and cherry-pick a commit onto one of your branches. Files move in and out of them as anywhere else: drag or cut a worktree's uncommitted files into any commit, or onto any branch to commit them there with no message yet (double-click its title to write one), drop your files on a worktree's commit or branch, and move, split off or uncommit the files of its commits. Its commits' files uncommit into the worktree itself, as that's where their checkout is. Select a linked worktree to watch its changes as they're written, its heading counting their lines as Main worktree's does; e opens a file from the worktree in your editor. Its files and hunks discard as yours do, by the hunk's button, ⌥⌘Z, ⌘⌫ or a right-click, but always ask first, as a worktree's discard can't be undone. On the Branches page, a branch a worktree has checked out offers Open worktree instead of Apply or Delete. Right-clicking its heading reveals or copies its folder, archives it to hide it, or deletes it from disk after asking, uncommitted files and all; its branch stays. Worktrees that exist when the setting goes on start archived, and Show an archived worktree… in the project's menu brings one back. A worktree with nothing uncommitted and no commit or checkout in the last 12 hours is inactive, and the project lists its inactive worktrees behind one "N inactive worktrees" row, which shows or hides them.
- **History.** The last row of each project lists what GitButler did to it, newest first, including what agents ran from the CLI. Select an operation to see the files it changed, then restore the project to how it was before it; the restore can be undone too. "Take snapshot" records the project as it is now, to come back to later.

Moving things works by drag and drop or by ⌘X on the source and ⌘V on the destination, or a click on the label each row shows while something is cut, saying what pasting there does:

| Move | onto | does |
|---|---|---|
| a commit | a branch | moves it to the top of that branch |
| a commit | another commit | moves it above that commit; hold ⌥ to squash instead, ⇧ to put it below |
| a commit | uncommitted changes | uncommits it |
| a commit | New branch, below the stacks while dragging | moves it into a new branch of its own (also in its menu) |
| uncommitted files | a commit | amends that commit |
| uncommitted files | a branch | picks that branch and those files for the next commit; a linked worktree's files, or onto a worktree's branch, commits them there with no message |
| a commit's file | another commit | moves the change between commits |
| a commit's file | uncommitted changes | uncommits just that file, a worktree commit's into that worktree |
| a branch | another branch | stacks it, with the branches above it, on top of that one; ⇧ puts it below that one instead |
| a branch | Move below, after a stack while dragging | puts it under the stack's last branch |
| a branch | a linked worktree | puts it under the worktree's branches |
| a hunk of uncommitted changes | a commit or branch | as its file would, with just that hunk |
| a hunk of a commit | another commit, or uncommitted changes | moves just that hunk, or uncommits it |

Drag a hunk by its header in the diff. Right-click a hunk or file header there, or press a file's ⋯ (in its header, or on its row in the file list while the pointer is on it), for the same moves as a menu, plus, in a commit, Split into a new commit (the hunk moves into a new commit right above, in one undoable step) and Discard from commit.

"Cherry-pick" in a commit's menu picks it up the same way, and ⌘V puts a copy on top of a branch or above a commit, leaving the original where it is.

Settings (⌘,; Escape or a click outside closes it) has a search box that finds a setting in any section. General picks light, dark or the system appearance, how large code shows in diffs, the editor files open in and the terminal; Git sets how often expanded projects fetch in the background; AI picks the provider (OpenAI, Anthropic, Ollama or LM Studio), GitButler's key or your own, and the model; Accounts signs in to GitButler and adds GitHub (in the browser, or a token), GitLab and Bitbucket accounts. All three are shared with GitButler's other apps. The top of the navigator shows the GitButler account: its picture, with a menu that names it, opens Accounts or signs out, or Sign in when nobody is. Signing in opens GitButler's page, which shows a token to paste back. Builds run from source sign in to GitButler's staging server. Project renames the project, changes its target branch (in the workspace, only with no branches applied), protects force pushes (a push that would drop commits someone else pushed stops and offers to push anyway), turns commit signing on and tests it, runs the repository's pre-commit, commit-msg, post-commit and pre-push hooks (off unless turned on, as in the desktop app), and removes the project from GitButler. Press e in the diff to open the file under the cursor in your editor at its hunk; the first time, a menu asks which editor. A project's menu opens it in the editor or the terminal, or opens its settings.

On a project hosted on a forge, a branch without a pull request offers Create pull request in its header and menu: a title and description start from the branch's only commit, or the repository's template, and the branch is pushed first if it needs it. Write with AI fills the title and description from its commits. A branch with an open pull request adds Merge (merge, squash or rebase, chosen in the dialog). Click a branch's CI glyph to check again.

Branch rows show a pull request's state (open, draft, merged or closed) and number, and a glyph for its checks. The app reads these from GitButler's forge cache, which it refreshes in the background every minute and after each push, using the GitHub account GitButler already has.

⌘F finds text in the diff, marking every match and stepping through them with Enter and ⇧Enter, unfolding a folded file to reach one. / (or the magnifier above the file list) filters the file list and the diff to paths with every word typed in them; Escape clears it. Long lines scroll sideways, a file's lines together and each side on its own in a side-by-side diff, unless wrapping is on (the wrap button over the diff, ⌥Z, or Settings); the button beside it draws changed lines without their green and red ground. Split over the diff (⌘B) shows diffs side by side, the old lines beside the new, and Unified one above the other. The button at the diff's top left hides the file list (f), and counts the files and their lines while the list is hidden; ⌘↩ and / bring it back, as the composer and the filter sit in it.

While a file scrolls, its header stays at the top of the diff until the next file pushes it off, and the file list marks that file as the current one, as but.dev's does; a file picked with a key or a click stays current until you scroll. Lists and diffs show a scrollbar while the pointer is over them; drag its thumb, or press the track to jump. Text in a diff selects like text anywhere: drag across lines, double-click a word, triple-click a line, shift-click to extend, and ⌘C copies it. Right-click the selection to copy it, find it in the diff when it's on one line, or open the file at that line; right-clicking a line outside it offers what its hunk's header does. A file row has its type's icon, its name with the folder dimmed, its line counts and a letter for added, modified, deleted or renamed, in design-core's change-status colours; folders have ui-react's teal folder. Files pick the same way commits do, one list at a time: ⌘-click (ctrl-click off macOS), ⇧-click, ⇧↑ ⇧↓ and ⌘A in the list, and Escape lets them go. Right-clicking a picked file, or its ⋯, offers what the one file's menu does for all of them (cut, discard, or from a commit uncommit, split off or discard), dragging one drags them all, and ⌘X and ⌘⌫ take them all too. File lists can show a tree of folders instead of a flat list, with the button beside the file count; folders holding nothing but one folder merge into one row (`src/backend`). The diff then lists its files in the tree's order, so j and k step through them as the list shows them, past folders folded shut. Right-click a folder to cut, discard or uncommit everything under it.

While something is cut or dragged, every row it could land on says what landing there would do ("Amend", "Move above", "Squash into" with ⌥ held, "Move below" with ⇧), and the rest step back. A commit selected in the app stays selected when an agent rewords or rebases it, as long as it keeps its change ID.

Changes to commits, branches and the main checkout's files undo with ⌘Z, and the snackbar names what was undone, including operations an agent ran from the CLI. Pushes, lands, merges and a linked worktree's discards and resolutions don't, nor does anything that moved a linked worktree's files: the oplog snapshots only the main checkout, so ⌘Z refuses rather than lose them. Changes show at once: what an operation takes away leaves the lists, and a new commit appears dimmed on its branch, until the reload after it shows the real result. Another operation asked for meanwhile waits its turn; the status bar names the one running, how long it's taking once that's noticeable, and how many wait. Quitting before they finish asks first. ⌘C copies the selection: a commit's id, a branch's name, or the path of the file under the diff cursor. Right-click any row for the rest, or press ⌘K for the command palette, which lists every command that applies where you are, with its keys. The status bar shows the few keys that matter for what has focus.

With no projects yet, the window says what the app is for and offers to add or clone a repository. File → Clone Repository… asks for a URL and a folder, clones it there and adds it. A project whose folder moved stays listed and says so, with Remove. A project with no target branch offers to pick one from its remote branches.

The Help menu links the docs, the release notes and where to report an issue, shows the folder GitButler keeps its settings in, and opens the command palette as the list of shortcuts. When a commit or amend has to leave changes out, the error says why for each, in plain words.

## How it's built

- `src/backend` is the only code that touches GitButler crates, and `src/backend/annotate.rs` the only code that touches deltoids. It turns `but-api` results into plain structs (`model.rs`) and diffs into hunks of lines (`diff.rs`), and runs every call on a tokio pool with large stacks, since GitButler's graph walks and push futures overflow the small stacks of GPUI's worker threads in debug builds.
- `src/state` holds the projects, selection, what's been cut and which commits you've opened. `load.rs` loads and watches workspaces, `background.rs` fetches and asks the forge on its own, and `seen.rs` tracks what you've looked at; `mutation.rs` runs one mutation at a time and queues the rest; `saved.rs` keeps what's been read in `gpui-state.json` in the app config directory.
- `src/navigator.rs` (its menus in `navigator/menu.rs`) and `src/detail/` (its file lists in `file_list.rs`) are the two halves of the window; `src/transfer.rs` decides what a drop or paste does, so both input methods agree. `build.rs` compiles in the file-type icons from `packages/ui-react`, and `src/ui/file_icons.rs` reads that package's map to pick one, so they match Lite and but.dev.
- `src/edits.rs`, `src/pr.rs`, `src/detail/resolve.rs` and `src/projects.rs` hold the actions on commits and branches, pull requests, conflicts and projects; `src/settings/` is the Settings window.
- `src/palette.rs` is the command palette, `src/overlays.rs` the menus, prompts, modals and snackbars above the window, and `src/status_bar.rs` the strip along the bottom.
- `src/ui` has the small components GPUI doesn't ship: buttons, a text field, a scrollbar, diff rows, and the empty states with ui-react's drawings, read from `packages/ui-react` and coloured for the theme.

It is a member of the main workspace, so `cargo check --workspace` catches `but-api` changes that break it. GPUI is a git dependency on Zed that brings around 900 crates and needs Rust 1.98. Only macOS builds the client. Elsewhere GPUI needs system libraries the workspace's Linux and Windows CI don't install, so `main` is a stub there and GPUI isn't compiled. Nothing else in the workspace depends on this crate.

## Development

- `GITBUTLER_GPUI_APPEARANCE=dark` (or `light`) overrides the system appearance.
- `E2E_TEST_APP_DATA_DIR=<dir>` points GitButler's app data and settings at a sandbox.
- Build with `cargo build -p but-gpui --features dev-script` and set `GITBUTLER_GPUI_SCRIPT=<file>` to replay clicks, drags and keystrokes and save screenshots of the window. `src/dev.rs` documents the commands.
