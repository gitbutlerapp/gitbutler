# GitButler on GPUI

An experimental native GitButler client built on [GPUI](https://gpui.rs), the UI framework behind Zed. It calls `but-api` in-process, so there is no Node runtime, IPC or JSON between the UI and GitButler.

## Run it

From the repository root, on macOS:

```bash
cargo build -p gitbutler-git --bins   # once: the askpass helper that push and fetch run
cargo run -p but-gpui
```

The project list comes from the app data of the build's channel, which is `dev` by default. Build with `CHANNEL=nightly` (or `release`) to see the projects of an installed GitButler.

## What you can do

The app is built for watching what coding agents change. Reading their changes comes first, and committing by hand is there when you need it.

The left side lists every project, under a filter in its header (/ goes to it). Typing in it leaves the projects, worktrees, branches and commits whose names match, under what holds them, folded or not: each word has to be in a row's name or in the name of what holds it, and one at least in its own, so "shop cart" finds shop's cart branch rather than all of shop. A branch matches by its name or its pull request's title, a commit by its title, an unwatched project by its name. Enter selects the first match and gives the list the keys, and Esc empties the filter, then leaves it. The eye on a project's left says whether the app watches it, and under the pointer shows what a click makes it: a watched project is loaded and kept current, in a card of its own; one struck through isn't loaded or watched. Watch and Stop watching in its right-click menu do the same, and double-clicking an unwatched project, or → on it, watches it. A watched project's chevron, at the row's right end, folds its card to the row, still loaded and kept current, which then sums up the card as an unwatched project's row does; double-click it, or press ← and →, to fold and unfold it, and ← on a folded one stops watching it. Folding over the selection moves it up to the project, and the folds stay for the next launch. Watched cards keep the order you give them, which the app remembers: drag a card by its heading over another's to put it before that one, a line in the gap showing where, or over More projects' to put it last, or use Move up and Move down in the heading's right-click menu. The button beside the account in the navigator's header can order them by name or by last activity instead (the one something last changed in first, so an agent at work brings its project to the top), and they don't move by hand then; the same menu folds every watched project or opens them all, and opens Settings. A newly watched project goes last, and the others stay by name. A watched project starts with Main worktree, which selects your uncommitted changes and counts them, a quiet "uncommitted" before the counts (a linked worktree's heading says it too, and a narrow navigator leaves the word out first), then its stacks, branches and commits, which its chevron folds away, and a faint line runs down from under each open row's chevron beside the rows it holds, as but.dev's sidebar draws them; with linked worktrees it heads a section of its own, as the next part says. An unwatched project's row sums up what it holds: uncommitted files, its worktrees' included (amber), unpushed commits (blue), commits the target has that you don't (amber; a merged pull request counts once, as the project's page lists it, and the tooltip adds how many commits the merges brought) and how many worktrees it has. A watched project's row keeps only the commits behind the target, as its rows count the rest, and a branch counts its commits only while they're hidden. Opening an unwatched project's page reads it once, without watching it, so its page and its right-click menu offer Update when its target has moved on; its row stays quiet, without the button a watched project's has. Hover a count to see what it counts. When a reload adds rows above the row under the pointer, like an agent's new commit, the list scrolls to keep that row where it is. A file watcher keeps watched projects current, reloading at most once a second while files keep changing, as when an agent works; the others aren't loaded at startup. They share a card under "More projects", the first eight then "N more", each with how long ago Git last recorded something done in it. A branch's commits fold the same way past eight; once unfolded, "Show fewer" at the end folds them again, staying under the pointer as "N more". Its heading folds the card away, adds a project, and under ⋯ sorts it by name or last activity and shows all of it or just the projects active in the last 7 days; the choices stay for the next launch. A green "active" dot marks a project whose files or commits changed in the last two minutes, and a teal dot marks commits you haven't opened yet, their titles in semibold, as it does a branch holding any, its name in semibold too, folded or not. Mark all as read in a branch's right-click menu clears its dots without opening each. A commit's menu, or the menu of several picked ones, offers Mark as read for those unread and Mark as unread for those read, both when the picks are some of each; a commit marked unread keeps its dot while it's open, until it's opened again. Commits the app itself rewrote don't count as new; a linked worktree's do, as an agent's work stands out there too. One amended elsewhere while the app is open, as by an agent, gets its dot back; one only rebased or only reworded doesn't, and neither does the commit on screen. A commit is known by its change ID, and by its author, time and message, which a rebase keeps even when Git's own drops the change ID.
The right side shows whatever is selected, under a bar on the window's grey ground, as but.dev's location bar: the button that shows or hides the navigator (.), then a breadcrumb naming the project, the worktree as the navigator heads it (Main worktree, or a linked worktree's name), and the branch, whose crumbs link back to them. Nothing sits on its right: what a page does to what it shows is in that thing's right-click menu, or beside its list's filter, as Fetch on the Branches page and Take snapshot on Operations history. ⌥⇧F fetches anywhere, and asks the forge about pull requests and CI again. Drag the right edge of the navigator or of a file list to resize it (a grey line marks the edge under the pointer), and double-click the edge to reset it; the widths are remembered.

- **Uncommitted changes.** Every changed file as a diff. j and k step through files, ↑ ↓ through hunks, space and shift-space page through the diff, and ⌥⌘Z throws a hunk away, with an Undo button in case you didn't mean it. The navigator's Main worktree row counts the lines they add and remove, in green and red, or how many files there are when none can be counted, as with binary files or more than 300 of them. ⌘↩ or "Commit…" opens the composer, where you check files or single hunks and pick a branch: the one you made last if you just made one, else the one you last committed to. With nothing changed, the composer still opens and makes an empty commit; opened on changes that something else, as an agent, commits meanwhile, it says so rather than make an empty one. The branch button, or ⇧⌘B while writing the message, opens a picker. Type to filter the branches and press Enter, or pick New branch… to make one for the commit. With Run Git hooks on in the project's settings, committing in the main checkout runs the repository's pre-commit hook, then commit-msg, which can rewrite the message, and either one failing stops the commit and shows what it printed. The post-commit hook runs after the commit, which stays even if the hook fails; an error then shows its output. Click a changed line's numbers to take just that line out, or, in a hunk that's out, to bring just that line in. The message you're writing stays with its project or linked worktree while the app runs, as what's checked does. The sparkle in the message box writes the message with AI from the checked changes, streaming it in; anything already in the box guides it. A file a merge left with conflict markers, as an update can, shows as conflicted and first, counted on Uncommitted changes in the navigator, and starts unchecked in the composer, as a commit refuses it while it's conflicted. Its conflicts show in place of the markers and resolve as a conflicted commit's do, between your changes and what the update brought (named after the target), or the sides the markers name after another merge: Apply in the banner above the files (⌘↩) writes what each keeps into the file, and marks it resolved once it has none left, in one step you can undo. Its menu can still mark it resolved as it is on disk, and discarding it takes it back to its last commit. When Git itself stopped partway through a rebase, merge, cherry-pick or revert, as an agent's can, a banner says so, and hovering it says how to finish it; the project's page does too.

  A changed image (PNG, JPEG, GIF, WebP, BMP or TIFF) shows before and after, side by side. So does an SVG, drawn sharp at its own size, an icon grown to 64 points so the change shows; the code button in its header shows its lines instead, and back. A submodule says which commit it points at, and which it pointed at before.

  Diffs are drawn like but.dev's. A file's header has its type's icon, its name with the folder dimmed, its line counts and five squares split green and red as they are, and the file the cursor is in has a tab on its left edge. Each line has one number, the old one for a removed line and the new one otherwise, and a changed line has a bar down its edge, solid for an addition and hatched for a removal. The cards sit on the pane's white ground, as but.dev's do, and side by side a line with nothing across from it faces a hatched gap. Code and the lines' greens and reds take GitHub's colours, and UI text and code are Inter and Geist Mono at design-core's regular weight, 460.

  Above each hunk a grey box counts the unchanged lines left out before it (`36 unmodified lines`). Clicking it, or the button beside the file's line counts, shows those lines too, so the whole file reads top to bottom; the button hides them again.

  Diffs mark the words that changed within a line, and the box above each hunk names the function or type it sits in (`impl Counter › pub fn bump(&mut self, by: i32) -> i32`). When the rest of that scope is short, 50 unchanged lines or fewer across its hunks, they show it whole, as deltoids does; a longer one keeps three lines of context, with the hunk's box naming it. Settings › Appearance › Whole scopes up to sets that limit to 20, 50 or 200 lines, and turning Semantic context off leaves out the names and the extra lines and skips reading the code for them. The extra lines are context only: picking, dragging and discarding act on the hunk as before. All of this comes from [deltoids](https://github.com/juanibiapina/deltoids), which parses the two sides with tree-sitter, in the 20 languages it knows (Rust, TypeScript, JavaScript, Python, Go and more, though not Svelte), for a file whose two sides come to 1 MB or less and that changes at most 4,000 lines.
- **A commit.** A header across the page, as but.dev draws it: the title, then who made it and when, its short ID (click to copy it), a quiet lock and "Signed" when it carries a GPG, SSH or X.509 signature (the tooltip names which; the app doesn't verify it), and whether it's pushed. An author shows as the same patterned circle in the same colour as on but.dev, drawn from their name. The button beside the title opens the rest of the message between those two lines, and double-clicking the title edits the message in place; what you type there waits for you while you look at other commits. Below sit its files and its diff. The ⋯ at the header's end opens the commit's right-click menu, which uncommits or discards it, adds an empty commit above or below (the selection stays where it was), starts a new branch ending at it, moves it into a new branch of its own, rewraps a message with lines too long for `git log`, and copies its ID, change ID or message. ⌘-click (ctrl-click off macOS) selects more commits along with it, and ⇧-click or ⇧↑ ⇧↓ selects a run of them from where the last other click left off, as in Finder, which the status bar counts. Dragging or cutting one of them takes them all, and a click without dragging selects just it; their right-click menu squashes them into the oldest, or into the one right-clicked, in its place, or uncommits them all.
- **A conflicted commit.** Its conflicts sit in its diff, where they are in each file, with its conflicted files first and marked Conflicted. Each one shows the lines of what the commit now sits on (named after the target, or "Commit below" further up a stack) and the commit's own lines, tinted as Lite and but.dev tint a merge conflict, with the words they differ in marked, and a button that shows how the lines were before either changed them. Above each, keep one side or both, edit what to keep in place (Return, or Edit), or have AI suggest a merge, which streams in as a suggestion to keep or change. A pick folds the conflict into what it keeps, with Change to pick again, and nothing changes until Apply in the commit's header (⌘↩) resolves every picked conflict in one step you can undo. A one-line banner above the files counts what's left, and says to start with an older conflicted commit in the stack when there is one; hovering it says why or what to do. Once a commit has none left, the stack's next conflicted commit comes up. 1, 2 and 3 keep the first side, the commit's or both, A suggests, and each pick moves on to the next conflict. For conflicts with no lines to pick, like a file one side deleted, run `but resolve <commit>` in a terminal. It checks the commit out, conflict markers and all, and the project then lists just "Editing a commit": its files, with their conflicts to pick between as above, Cancel to put the commit back as it was, and Finish to commit the files in its place (asking first while any are still conflicted). Until then the app turns down other operations on the project, apart from fetching. A branch with conflicted commits says how many on its page, and its Resolve goes to the oldest in its stack, which can be in a branch below.
- **A branch.** Its commits and combined diff, under a header across the page as a commit's has, so stepping between a branch and its commits moves nothing below: its name, how many commits it has, where they stand against its remote and any conflicted. A stack's page has one too. A branch starts folded, its commits behind a count, unless Settings › Appearance › Show branches' commits is on; one of its commits being selected shows them anyway. Click the chevron before its glyph, double-click it, or press → to show its commits, and again, or ←, to hide them; a branch with no commits has a dot there instead, and says "empty" after its name, as but.dev's does. Hiding them over a selected commit selects the branch. A stack of two or more branches sits under a "Stack of N" caption, its branches a step in. Selecting the caption shows what its branches change together, as one diff; its chevron, a double-click, or ← and → fold them away, and folded, it names its top branch, to tell it from another stack as tall, counts their unpushed commits and says when they last changed. ← from a branch in it goes up to it. Its tooltip names the branches, top first. Right-click it to push the stack, land it on the target, start a new branch on top, or unapply it: each acts through its top branch, which takes the ones below along, as the branch's own menu does. A linked worktree's stack only folds and takes a new branch on top. Its header says how it stands against its remote in plain words: on the remote, so many to push, so many to pull (and to push), or rewritten and needing a force push; one only behind its remote isn't offered a force push, as pulling is all it needs. When its remote has commits it doesn't, as when a teammate or an agent elsewhere pushed, its page lists them and Pull brings them in with its own commits on top. Click one to see its files and diff in place of the branch's, its title added to the breadcrumb, and again to go back; right-click it to cherry-pick it or copy its ID, as on the Branches page. After a rewrite here, the remote's older versions of those commits are left out rather than brought back beside the new ones, and its new commits go after the rewritten ones they were made on, in the remote's order; and a force push asks before dropping them, and any force push fetches first and stops if someone pushed since the last fetch or the remote has commits that weren't shown; when that would leave its commits conflicted it stops and says so, with Pull anyway to go ahead, which checks again first; its menu can also replace the branch with the remote's version instead. A branch with others stacked on it can't pull yet. Its right-click menu adds a branch on top or below, an empty commit on top, squashes all its commits into one, takes it out of its stack, or unapplies it. The bottom branch of a stack can land on the target, its commits going straight onto it and pushed, skipping review; from the top branch the whole stack lands. Both ask first, as a push can't be undone. With Land branches directly on in the project's settings, its menu's Land works with or without a forge.
- **A branch's pull request.** A branch with one has two tabs under its header, Changes (with how many files) and Pull request (with a glyph while its checks run or fail), as but.dev's page has; the tab picked stays picked from branch to branch. The Pull request tab shows its title, number, state, author, the branch it merges into, when it last changed, labels and who's been asked to review it, with a button to open it; its description, less the template's comments, formatted from its Markdown: headings, bold, code, lists and task boxes, quotes and links, which open only to the web or mail and show where they go on hover, while images are never loaded, showing their words instead, and HTML shows only its text; and its checks, failed and running ones first, each opening its log, and the ones that passed or were skipped folded into one line. It reads only GitButler's forge cache, so it opens instantly, and for an open one says when the forge was last asked (Checked 5m ago, which asks again); when asking failed and what it shows is over 30 minutes old, a banner says how old, with Try again. Threads, reviews and comments aren't shown, as the cache doesn't keep them; Merge stays in the page's top bar.
- **A project.** Under a header with its name and an icon, which opens a picker of emoji to give it one, as but.dev's repository page does (search by name, Return takes the first, Remove icon clears it); the navigator shows the emoji before its name, and the app keeps it with its other preferences. Where it is, when it last fetched (and why a fetch failed, or that it has no remote to fetch from), a nudge to connect an account when it's on a forge none is connected for, and its target's history: the commits new on the target first, then the ones your workspace already has, one that landed a pull request named by the request's title with a merge glyph, as Lite names them (its number, merge commit and ID on hover), each with the picture of who wrote it beside its age, as the Branches page has, paging further back on request. Select one to see its diff; the breadcrumbs name the target and the commit. One that landed a pull request has Changes and Pull request tabs over its diff, as a branch on the Branches page has, without CI checks. Clicking when it last fetched fetches again, and Update (the button on the project's card, or ⌥⇧R) rebases every stack onto the target's new commits. Update first works out whether rebasing would conflict any commits or uncommitted changes, and stops with Update anyway when it would, which goes ahead only while that's still all it would conflict. Afterwards it says which branches have conflicted commits, selecting the first, and which landed branches it removed. A new project starts with one branch checked out rather than the GitButler workspace, as in the desktop app, and its page says it's working on that branch directly. Switch to the workspace leaves it for the workspace, to work on several branches at once. Until then a new branch goes on top of the one checked out and is checked out in its place, and there's nothing to unapply.
- **Branches.** Next to Operations history at the end of each project: the branches the workspace doesn't have applied, newest first as in Lite, local ones and the ones only a remote has (like a teammate's, named as the remote has it, origin/…) alike, and a stack's branches together under a caption, a step in; clicking the caption folds them away, and folded, it names its top branch. An open branch lists only its own commits, not those of the branches below it. There's a filter by name, pull request title or author (/ goes to it). Its filter menu, as Lite's, leaves out branches with no commits of their own until Include empty branches is ticked, and Only local branches leaves out the remote ones. The button beside it fetches, and asks the forge about pull requests and CI again. Hovering Branches in the navigator says it's the branches not applied in your workspace. A branch with a pull request is named by its title, as in the navigator, with its name and number on hover. Beside its age, the picture of who made its newest commit, the pattern but.dev draws for them, picks out a teammate's branches at a glance; hovering it names them. Each shows what it changes against the target, as its pull request would, and Apply to workspace adds it beside your other branches (a remote branch gets a local branch first), while Switch to branch leaves the workspace to work on just it, checked out on its own, as Lite's does; Switch to the workspace, on the project's page, brings the others back. A branch with a pull request has Changes and Pull request tabs over its diff, as an applied branch's page has, the tab picked staying picked; the Pull request tab leaves out CI checks, as the app asks the forge about those only for applied branches, so the cache's would be stale. Local branches can be deleted. A branch's commits fold under it behind a chevron, as in the navigator: click the chevron, double-click the branch, or press → and ←, and ↑ and ↓ (or j and k) step through the list, as they do through Operations history's. Right-click a branch to apply it (or open the linked worktree that has it checked out), open its pull request, copy its name or delete it. Select a commit to see it on its own, then drag it onto a branch or commit in the workspace, or pick Cherry-pick in its right-click menu and press ⌘V there, to copy just that commit in. ⌘-click picks more of the branch's commits along with it, and ⇧-click the ones between, as in the navigator; dragging one of them, or Cherry-pick on one, takes them all, and they go in together as one step to undo, oldest first, in the order the branch has them.
- **Linked worktrees.** With Linked worktrees on in Settings (GitButler's experimental worktree support), a project with linked worktrees, like the ones agents work in, lists each worktree in a section of its own, separated by dashed lines. "Main worktree" comes first, over your stacks; each linked worktree follows, over the branches and commits made in it, from the branch it has checked out down to where it started. Commits the target already has are left out. Selecting a worktree's heading shows its uncommitted changes, which the heading counts. Its chevron, a double-click, or ← and → fold its branches; folded, the heading also counts their unpushed commits, and Main worktree's shows a dot for unread commits. Folding over the selection moves it up to the heading, and ← from a closed branch goes there too. A green dot on a heading means its files changed in the last two minutes, as an agent at work does (the project counts as active then too). Its commits drag, cut and paste as yours do: reorder or squash them, move them between it and your stacks, or drop one on the worktree's heading to uncommit it there. Rewriting the branch the worktree has checked out takes the worktree along and updates its files, and is refused when that would overwrite its uncommitted changes. Its branches move only within its lane, and yours go under its branches from its heading (see below); a branch moved across would leave the worktree detached and bring along the commits it started from. Its commits and branches are edited from here as yours are too: reword, discard, uncommit, squash, add empty commits, select several with ⌘ and ⇧, rename a branch (the worktree follows the new name) or move a commit to a new branch. What reaches past the worktree asks you to do it there: pushing, pulling, pull requests, landing and unapplying. None of these undo either. New branches go on top of or below its branches, as on yours; one on top of the branch it has checked out becomes its checkout, so its next commits go there, as the prompt says. A branch stacked under the one it has checked out can be deleted, its commits joining that one, as in Lite; the one checked out stays with the worktree, and the delete can't be undone, as the oplog doesn't keep a worktree's branches. Files move in and out of them as anywhere else: drag or cut a worktree's uncommitted files into any commit, or onto any branch to commit them there with no message yet (double-click its title to write one), drop your files on a worktree's commit or branch, and move, split off or uncommit the files of its commits. Its commits' files uncommit into the worktree itself, as that's where their checkout is. Select a linked worktree to watch its changes as they're written, its heading counting their lines as Main worktree's does; e opens a file from the worktree in your editor. Its page is laid out as Main worktree's, and commits the same way: Commit… or ⌘↩ opens the commit box, whose checked files, hunks and lines go on the branch the worktree has checked out (there's no other to pick), and Amend adds them to that branch's newest commit. ⌘↩ from one of its branches or commits comes here, rather than to Main worktree. Its files and hunks discard as yours do, by the hunk's button, ⌥⌘Z, ⌘⌫ or a right-click, but always ask first, as a worktree's discard can't be undone. On the Branches page, a branch a worktree has checked out offers Open worktree instead of Apply or Delete. Right-clicking its heading reveals or copies its folder, archives it to hide it, or deletes it from disk after asking, uncommitted files and all; its branch stays. Worktrees that exist when the setting goes on start archived, and Show an archived worktree… in the project's menu brings one back. A worktree with nothing uncommitted and no commit or checkout in the last 12 hours is inactive, and the project lists its inactive worktrees behind one "N inactive worktrees" row, which shows or hides them.
- **Network worktrees.** Signed in to your mesh (Settings > General), a watched project's card lists its checkouts on your other machines after its own worktrees, under a Network worktrees heading, and draws them as it draws worktrees, with a computer for an icon. Each is named by its machine, with the worktree or folder name when the machine has more than one, and shows where it is on hover. It's faint while that machine is offline, counts its uncommitted lines, and has a green dot while something there changed in the last two minutes. Under each are its branches, counting unpushed commits, and under an open branch its commits. A chevron, a double-click, → or ← folds them as a worktree's, and branches start folded or open as Settings say local ones do. They start folded under the heading, which counts them; clicking it shows them, or folds them again, and the app remembers which projects show them. Work this machine already has, and work another checkout shows too, is listed once. Selecting something of a project's elsewhere fetches its branches here with `but mesh fetch`, from the copy the mesh keeps (also while that machine is offline), one at a time and the selected one first, into refs of the mesh's own, checking nothing out; a branch whose newest commit is here already isn't fetched. Until a branch is here its diff says it's fetching, or why it couldn't. A branch shows what it changes against the target, and a commit its own diff; a new tip reported later fetches it again. Uncommitted files' diffs stay on that machine, so a checkout lists them beside the diff, with Open on but.dev. The right-click menu opens a checkout or branch on but.dev, copies a checkout's path, or offers Apply here for a branch, which brings its commits over, outside the project's queue so a slow network holds up nothing else, and applies it to your workspace, named `<branch>-from-<machine>` when one here has its name. It works while that machine is offline too, from the copy the mesh keeps. The filter finds a checkout by its machine or worktree name, or by its branches' names. The app reads the mesh every minute, and at once when a project starts being watched; a read that fails keeps the last one, so a network blip or a broken daemon leaves the card as it was. While signed in, each project watched here is added to the mesh daemon's list if it isn't on it, so your other machines see its work; the daemon watches its files and reports a change within seconds. It all goes through the `but mesh` command-line tool (`but-mesh` on the `PATH` or in `~/.local/bin`), so without it nothing shows.
- **Operations history.** The last row of each project lists what GitButler did to it, newest first under each day, including what agents ran from the CLI: each operation as what it was done to, after a glyph for what it did (a commit made, changes amended into one, commits squashed, something reworded or renamed, thrown away, done to a branch, brought in from the target, taken back, a snapshot), and its time, faint. The glyph is green for what the operation added, blue for what it rewrote, red for what it threw away and amber for what it took back, and hovering it names the operation, so every row leads with its commit or branch and a run of commits made reads as the commits. One with nothing to name, as a commit that failed to sign, shows the operation's name, faint. What an operation was done to comes from comparing its snapshot with the next one, or with the workspace now for the newest, with the workspace applied or one branch checked out on its own, matching commits by change ID so a rebase alone changes nothing, and telling an amend by the same parent with other changes: the commit it made, amended or reworded, the one a squash took away and the one it went into, how many it cherry-picked, the branch it created, renamed or unapplied, how many commits an update brought from the target; else what the log says. `but amend` logs an amend as a squash, so one that took no commit away is listed as the amend it was. An undo, redo or restore shows what the operation it took back was done to, its glyph's hover naming that operation. Work done outside GitButler between two operations counts as the later one's; a linked worktree's isn't in the snapshots, so what was done there shows only by the log's name for it. Select an operation to see, over the files it changed, a header as a commit's: what it was and when, the branch it was on, and each commit or branch it changed, an amended one marked so and a reworded one with its old title; a commit the workspace still has opens on a click. Restore the project to how it was before it from its right-click menu or the header's ⋯, which also copies its snapshot's ID; the restore can be undone too, and it refuses, as ⌘Z does, to go back past what moved a linked worktree. Above the list, a filter (/ goes to it) finds operations by what they did or to what, the menu beside it picks which kinds show (commits made, commits rewritten, changes thrown away, branches, updates, undos and restores, snapshots), and + takes a snapshot of the project as it is now, to come back to later, with a message to say what it's for if you give one. A snapshot reads as its message, or "Manual snapshot", beside a camera.

Moving things works by drag and drop or by ⌘X on the source and ⌘V on the destination:

| Move | onto | does |
|---|---|---|
| a commit, or the selected ones | a branch | moves them to the top of that branch |
| a commit, or the selected ones | another commit | moves them there, between the two commits under the pointer; on a commit's middle, squashes them in |
| a commit, or the selected ones | uncommitted changes | uncommits them, a worktree commit's into that worktree |
| a commit | New branch, below the stacks and any linked worktrees while dragging | moves it into a new branch of its own (also in its menu) |
| uncommitted files | a commit | amends that commit |
| uncommitted files | a branch | picks that branch and those files for the next commit; a linked worktree's files, or onto a worktree's branch, commits them there with no message |
| a commit's file | another commit | moves the change between commits |
| a commit's file | uncommitted changes | uncommits just that file, a worktree commit's into that worktree |
| a branch | another branch | stacks it, with the branches above it, on top of that one; ⇧ puts it below that one instead. A linked worktree's branches only move within its lane |
| a branch | Move below, after a stack while dragging | puts it under the stack's last branch |
| a branch | a linked worktree | puts it under the worktree's branches |
| a hunk of uncommitted changes | a commit or branch | as its file would, with just that hunk |
| a hunk of a commit | another commit, or uncommitted changes | moves just that hunk, or uncommits it |

Drag a hunk by its header in the diff. Right-click a hunk or file header there, or press a file's ⋯ (in its header, or on its row in the file list while the pointer is on it), for the same moves as a menu, plus, in a commit, Split into a new commit (the hunk moves into a new commit right above, in one undoable step) and Discard from commit. A file's menu also opens it in your editor, and a file's or folder's copies its path or full path and reveals it in Finder, even where nothing can change it, as on the Branches page or in a commit of the target; a file that isn't on disk, as one deleted or only a branch outside the workspace has, only copies its path.

"Cherry-pick" in a commit's menu picks it up the same way, and ⌘V puts a copy on top of a branch or above a commit, leaving the original where it is.

Settings (⌘,; Escape or a click outside closes it) is laid out as Lite's: its pages down the left, the app's and then the selected project's under the project's name (which picks another project's), and each page a column of cards, a setting a row, with a search box that finds a setting on any page. General signs in to GitButler and to your mesh, and picks the editor files open in and the terminal; Appearance picks light, dark or the system appearance, and how diffs show (code size, wrapping, side by side); AI picks the provider (OpenAI, Anthropic, Ollama or LM Studio), GitButler's key or your own, and the model; Git sets how often expanded projects fetch in the background; Integrations adds GitHub (in the browser, or a token), GitLab and Bitbucket accounts; Experimental turns on linked worktrees. These are shared with GitButler's other apps, but for what's only this app's. The top of the navigator shows the GitButler account: its picture, with a menu that names it, opens Settings or signs out, or Sign in when nobody is. Signing in opens GitButler's page, which shows a token to paste back. It signs in to GitButler's production server, even built from source, unless `GITBUTLER_API_URL` names another, as for staging. The Mesh row signs this machine in to the mesh of your machines: the browser opens to approve it, and the mesh daemon starts. Signed in, it says as whom and as which machine, and warns when the daemon isn't running; Sign out asks first, then stops the daemon and takes the machine out of the mesh. The project's Project page renames it, changes its target branch (in the workspace, only with no branches applied), picks its forge when the remote's host doesn't name one, as for a self-hosted forge (one it names can't be changed, as in GitButler's other apps, which share the pick), and removes it from GitButler; its Git page protects force pushes (a push that would drop commits someone else pushed stops and offers to push anyway), runs the repository's pre-commit, commit-msg, post-commit and pre-push hooks (off unless turned on, as in the desktop app), lands branches directly, and turns commit signing on and tests it. Press e in the diff to open the file under the cursor in your editor at its hunk; the first time, a menu asks which editor. A project's menu opens it in the editor or the terminal, or opens its settings.

On a project hosted on a forge, a branch without a pull request offers Create pull request in its menu: a title and description start from the branch's only commit, or the repository's template, and the branch is pushed first if it needs it. Write with AI fills the title and description from its commits. A branch with an open pull request adds Merge (merge, squash or rebase, chosen in the dialog). Click a branch's checks glyph to check again.

A branch with a pull request is named by its title, in the navigator, a folded stack's caption, a drag's pill and a Move below zone, with a glyph for its state (open, draft, merged or closed); hovering the title shows the branch's name, the number and how its checks stand. A glyph for the checks shows only while they run or after one fails. A branch keeps its name until the title is known. The app reads these from GitButler's forge cache, which it refreshes in the background every minute and after each push, using the GitHub account GitButler already has, so a row never waits on the network, and offline it keeps the titles it last read.

⌘F finds text in the diff, in every line it shows, unchanged ones included, as a scope around a hunk or a file shown whole, marking every match and stepping through them with Enter and ⇧Enter, unfolding a folded file to reach one. / (or the magnifier above the file list) filters the file list and the diff to paths with every word typed in them; Escape clears it. Long lines scroll sideways, a file's lines together and each side on its own in a side-by-side diff, unless wrapping is on (the wrap button over the diff, ⌥Z, or Settings); the button beside it draws changed lines without their green and red ground. Split over the diff (⌘B) shows diffs side by side, the old lines beside the new, and Unified one above the other. The button at the diff's top left hides the file list (f), and counts the files and their lines while the list is hidden; resting on it a moment (100ms) then lists them in a popover, where clicking one scrolls the diff to it and leaves the popover open for the next. ⌘↩ and / bring the list back, as the composer and the filter sit in it. On the Branches, Operations history and project pages, whose column is their own list, the button can't show the files beside the diff; it counts them and lists them on hover.

While a file scrolls, its header stays at the top of the diff until the next file pushes it off, and the file list marks that file as the current one, as but.dev's does; a file picked with a key or a click stays current until you scroll. Lists and diffs show a scrollbar while the pointer is over them; drag its thumb, or press the track to jump. Text in a diff selects like text anywhere: drag across lines, double-click a word, triple-click a line, shift-click to extend, and ⌘C copies it. Right-click the selection to copy it, find it in the diff when it's on one line, or open the file at that line; right-clicking a line outside it offers what its hunk's header does. A file row has its type's icon, its name with the folder dimmed, its line counts and a letter for added, modified, deleted or renamed, in design-core's change-status colours; folders have ui-react's teal folder. Files select the same way commits do, one list at a time: ⌘-click (ctrl-click off macOS), ⇧-click, ⇧↑ ⇧↓ and ⌘A in the list, and Escape lets them go. Right-clicking a selected file, or its ⋯, offers what the one file's menu does for all of them (cut, discard, or from a commit uncommit, split off or discard), dragging one drags them all, and ⌘X and ⌘⌫ take them all too. File lists can show a tree of folders instead of a flat list, from the ⋯ beside the file count, as but.dev's do, and sort their files by name or by when each was last written, newest first (a commit's files, which have no write time, stay by name); folders holding nothing but one folder merge into one row (`src/backend`). Resting the pointer on a folder shows the lines its files add and remove. The diff then lists its files in the tree's order, so j and k step through them as the list shows them, past folders folded shut. Right-click a folder to cut, discard or uncommit everything under it.

Hunks and lines move the same way. A changed line shows a grip left of its number while the pointer's on it; hovering the grip outlines what it takes, the run of changed lines around it, and dragging it lands that on a commit (Amend, Move into), Main worktree (Uncommit) or a branch, as a file lands. Click a line's number to select it, ⇧-click or drag down the numbers to select a run, and ⌘-click to add or drop one; a selected line's grip takes all the selected lines, and the status bar counts them. Escape, a click elsewhere in the diff, or dragging anything else lets them go. Right-clicking a changed line offers Cut, Uncommit, Split into a new commit and Discard for what its grip takes, and an unchanged line for its whole hunk. ⌘X in the diff cuts the selected lines, or else the hunk under the cursor, to paste with ⌘V. What an operation takes leaves the diff at once, lines and all. Lines and hunks go by their place in the file, so once something else writes to it, as an agent does, a cut or drag of some of it is let go, and committing, amending or discarding some of it asks you to try again on the fresh diff rather than take whatever lies there now.

While dragging, the row under the pointer shows where letting go lands, a line between two commits or an outline around what it goes into, and the pill at the pointer says what letting go does ("Move here", "Squash into", "Amend"). Near the navigator's top or bottom edge, or past it, the navigator scrolls that way, faster the closer the pointer gets, and where letting go lands follows the rows as they pass under it. A commit's top and bottom quarters go above and below it, its middle squashes into it. While something is cut, the selected row shows where ⌘V puts it. Rows it can't go on step back. A commit selected in the app stays selected when an agent rewords or rebases it, as long as it keeps its change ID, and so does a drag in progress; a branch's diff stays scrolled where it was. A branch an agent renames, in a linked worktree too, stays selected and open or folded as it was, and a pull request being written for it follows; a Rename or New branch on top prompt open on it closes, and the commit target picker and Go to branch say so if it's picked. When an agent checks out another branch in a linked worktree, that worktree stays selected.

Changes to commits, branches and the main checkout's files undo with ⌘Z, and the snackbar names what was undone, including operations an agent ran from the CLI. While the snackbar offers to undo another project's operation, as one that finished after you moved on, ⌘Z takes that one back. Pushes, lands, merges and a linked worktree's discards and resolutions don't, nor does anything that moved a linked worktree's files or rewrote its branches: the oplog snapshots only the main checkout, so ⌘Z refuses rather than lose them. Changes show at once: what an operation takes away leaves the lists (files, commits, a stack being unapplied or landed, a bottom branch being landed with its commits, a worktree being archived or deleted, a branch deleted from the Branches page; one deleted from its stack, its commits joining the branch above, or the one below when it was the top), a new commit appears where it goes, as do an empty one and one moved or cherry-picked there, dimmed only if the operation is still running 400ms later, a new message or branch name shows in place, and a pull request being merged shows merged, until the reload after it shows the real result. A selection on what leaves moves to Main worktree, and back if the operation fails. After an operation that changes only commits and branches (editing a message, adding an empty commit, making, naming or renaming a branch) that reload reads just those, keeping the uncommitted files as shown, as reading them is most of a reload; the file watcher still reads everything once it sees the operation's writes. Another operation asked for meanwhile waits its turn, though a fetch, an update or a branch's pull asked for again while one waits or runs is let be, as it would do nothing more, and its button says Fetching… or Updating… until it's done; the status bar says what the one running is doing (Rebasing… for an update, Pushing main…), in which project when it's another's, how many seconds it has taken once that's noticeable, and how many wait. Quitting before they finish asks first. ⌘C copies the selection: a commit's id, a branch's name, or the path of the file under the diff cursor. A project's or its main worktree's right-click menu starts a branch: New branch in workspace (⌘N), beside the others, or New branch and switch to it, made at the target and checked out on its own, leaving the workspace, as an agent's single-branch work starts. Right-click any row for the rest, or press ⌘K for the command palette, which lists every command that applies where you are, with its keys. The status bar shows the few keys that matter for what has focus, quietly, as plain text: in the navigator those for the selected row (a project's fetch and update, a branch's push, pull request and rename, a commit's cut, message and uncommit), in the diff its own. Its left end says what's running or cut, else where you are, as an editor's status bar names the file and line: in the diff, the file under the cursor, its place among the files and its hunk; elsewhere, the project's standing against its target and, once the app has fetched it, how long ago.

With no projects yet, the window says what the app is for and offers to add or clone a repository. File → Clone Repository… asks for a URL and a folder, clones it there and adds it. A project whose folder moved stays listed and says so, with Remove. A project with no target branch offers to pick one from its remote branches.

The Help menu links the docs, the release notes and where to report an issue, shows the folder GitButler keeps its settings in, and opens the command palette as the list of shortcuts. When a commit or amend has to leave changes out, the error says why for each, in plain words.

## How it's built

- `src/backend` is the only code that touches GitButler crates, and `src/backend/annotate.rs` the only code that touches deltoids. It turns `but-api` results into plain structs (`model.rs`) and diffs into hunks of lines (`diff.rs`), and runs every call on a tokio pool with large stacks, since GitButler's graph walks and push futures overflow the small stacks of GPUI's worker threads in debug builds.
- `src/state` holds the projects, selection, what's been cut and which commits you've opened. `load.rs` loads and watches workspaces, `background.rs` fetches and asks the forge on its own, and `seen.rs` tracks what you've looked at; `mutation.rs` runs a project's mutations one at a time and queues the rest; `saved.rs` keeps what's been read in `gpui-state.json` in the app config directory.
- `src/navigator.rs` (its menus in `navigator/menu.rs`) and `src/detail/` (its file lists in `file_list.rs`) are the two halves of the window; `src/transfer.rs` decides what a drop or paste does, so both input methods agree. `build.rs` compiles in the file-type icons from `packages/ui-react`, and `src/ui/file_icons.rs` reads that package's map to pick one, so they match Lite and but.dev.
- `src/backend/mesh.rs` runs the `but-mesh` program for the mesh, reading its JSON, as the mesh has no library; `src/state/mesh.rs` polls it, `src/navigator/mesh.rs` draws each card's checkouts elsewhere, `src/detail/machine.rs` fetches and shows what's selected of them and `src/settings/mesh.rs` is its Settings row. AGENTS.md has the rules that keep it apart from the rest and harmless when the mesh misbehaves.
- `src/edits.rs`, `src/pr.rs`, `src/detail/resolve.rs` and `src/projects.rs` hold the actions on commits and branches, pull requests, conflicts and projects; `src/settings/` is the Settings window.
- `src/palette.rs` is the command palette, `src/overlays.rs` the menus, prompts, modals and snackbars above the window, and `src/status_bar.rs` the strip along the bottom.
- `src/ui` has the small components GPUI doesn't ship: buttons, a text field, a scrollbar, diff rows, and the empty states with ui-react's drawings, read from `packages/ui-react` and coloured for the theme.

It is a member of the main workspace, so `cargo check --workspace` catches `but-api` changes that break it. GPUI is a git dependency on Zed that brings around 900 crates and needs Rust 1.98. Only macOS builds the client. Elsewhere GPUI needs system libraries the workspace's Linux and Windows CI don't install, so `main` is a stub there and GPUI isn't compiled. The desktop app's binary can start it too: built with `gitbutler-tauri`'s `builtin-gpui` feature on macOS, it runs this client instead of the web one when started with `--gpui`, or always when GitButler's `featureFlags.gpui` setting is on, which only this client's Settings › Experimental › Open this app at start shows (or an edit of `settings.json`), on the same settings, accounts and keychain entries. Started that way, it asks the web app's update feed for a newer version as often as the web app would, and New version beside Sign in restarts into the web app once to install it; the web app's own restart after installing comes back here when that setting is on.

## Development

- `GITBUTLER_GPUI_APPEARANCE=dark` (or `light`) overrides the system appearance.
- `E2E_TEST_APP_DATA_DIR=<dir>` points GitButler's app data and settings at a sandbox.
- Build with `cargo build -p but-gpui --features dev-script` and set `GITBUTLER_GPUI_SCRIPT=<file>` to replay clicks, drags and keystrokes and save screenshots of the window. `src/dev.rs` documents the commands.
